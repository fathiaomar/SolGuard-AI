# Security Policy

## Reporting a Vulnerability

If you discover a security vulnerability in **SolGuard AI** ([`fathiaomar/SolGuard-AI`](https://github.com/fathiaomar/SolGuard-AI)), please **do not** disclose it publicly in a GitHub issue, discussion, or pull request until it has been reviewed and addressed.

### How to Submit a Private Report
- Reach out privately to the repository maintainer (**Fathia Omar**, `@fathiaomar`) via GitHub or your direct contact channel.
- Please include:
  - A clear summary of the vulnerability and where it occurs (routes, components, services, or `supabase-schema.sql`)
  - Step-by-step instructions or a safe proof-of-concept to reproduce the issue
  - The potential impact (such as authentication/session exposure, Row Level Security bypass, unauthorized access to projects/contracts/audits, cross-site scripting, or secret leakage)
  - Any suggested mitigation or fix, if you have one

### Response & Triage
- Reports are reviewed in order of severity and potential impact.
- You can expect an acknowledgment and triage update as soon as possible, along with coordination on remediation before any public disclosure.

## Scope & Important Limitations

**SolGuard AI** is a Solidity project management, pattern-review, and triage workspace—not a formal verifier, compiler guarantee, or substitute for an independent smart contract security audit.

### Static Pattern Checks & AI Review Caveats
- **Bounded pattern checks:** Static pattern checks scan for a bounded set of Solidity patterns and source-level indicators; they do not guarantee a contract is free of bugs or vulnerabilities.
- **Triage scores & estimates:** Severity labels, report scores, and gas or best-practice prompts are review and triage aids—not compiler-measured runtime results, formal proofs, or probabilities of exploitation.
- **AI-assisted findings:** AI review outputs are generated by the configured external model (`OPENAI_API_KEY` / `OPENAI_MODEL`) after explicit user authorization and may be incomplete, imprecise, or incorrect. Always validate smart contracts thoroughly with testing and qualified human security reviewers before deploying to mainnet.

### Secrets & Environment Variables
- Never commit `.env`, `.env.local`, API keys, database passwords, or privileged service-role credentials to version control.
- Keep `OPENAI_API_KEY` and any other server-side credentials strictly on the server—never expose them through `NEXT_PUBLIC_` variables or client-side code.
- Rotate any credential immediately if you suspect it was exposed or leaked.

### Contract & User Data Confidentiality
- Do not upload proprietary, confidential, or third-party smart contract source code to a hosted deployment or external AI provider unless you have explicit authorization to share it.
- Be mindful that deleting a project removes its associated contracts, audits, and reports according to the repository's schema and deletion logic.

### Deployment, Supabase & Auth Hygiene
- Serve the application over **HTTPS** in production environments.
- Configure **Supabase Authentication** properly (`Email` / *Confirm email*, `Site URL`, `Redirect URLs` such as `/auth/callback`, and custom SMTP settings for production delivery).
- Apply `supabase-schema.sql` and verify **Row Level Security (RLS)** policies and storage permissions so user data remains isolated before opening a deployment to external users.
